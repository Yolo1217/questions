## 三、缺陷报告

### D-1 同一伪造流水号重复重推会刷爆支付异常表（低）

- 级别：**低**（不造成资损，属可用性/审计卫生问题）。
- 复现步骤：
  1. 对任意订单号/不存在订单号，用错误签名向 `POST /api/v1/pay/notify` 重推**同一渠道流水号**（如 `CH-FLOOD`）3 次；
  2. 查询 `GET /api/v1/cs/exceptions`。
- 实际：异常表新增 **3 条**独立的待处理「验签失败」工单；`FindExceptionByTradeNo` 反查只取最新一条，历史工单持续堆积，伪造流量可无限刷客服工作台。
- 期望：同一渠道流水号的重复伪造重推应去重（如按 `trade_no+type` 幂等，仅累加命中次数），或至少合并为一条工单。
- 证据：`TestForgedSignatureRepeatDoesNotFloodExceptionDesk` 失败输出（got 3）。
- 备注：代码注释称"防重放证据"，每次留痕或有故意成分；但工单不去重 + 反查只取最新，客服闭环会被淹没，建议按低优先级整改。

### D-2 超时关单与支付回调竞态窗口内，迟到支付可能既不入账也不落异常（中）

- 级别：**中**（窗口毫秒级、单实例 5 秒轮询下概率低，但一旦命中即资金悬置，违反 S4/E08 口径）。
- 复现交错（并发，一次实测命中）：
  1. `PayNotify` 步骤 3 读到订单状态 `CREATED`（验签通过、回调已落库）；
  2. `SweepExpired` 此刻将订单 `CREATED→CLOSED` 并释放库存；
  3. `PayNotify` 步骤 5 条件更新 `CREATED→PAID` rows=0，落入"并发通知已被其他请求处理"分支，回调标记 DONE，返回成功。
- 实际结果：订单 CLOSED、库存已释放、**无支付流水、无「关单后到账」异常**；渠道收到成功后不再重推。该笔真实支付在异常工作台没有闭环入口（`HandleException` 需要异常记录存在），资金悬置仅可通过回调反查发现。
- 期望：迁移失败时回调状态不应置 DONE 并返回"重复"成功；应比照 CLOSED 分支落「关单后到账」异常（或至少落 FAILED + 异常）。
- 证据：完整回归第一轮 `--- FAIL: TestSweepAndPayRaceSingleOutcome (0.02s) ... closed outcome must record late-pay exception, got []`（测试随后收敛为只断言所有交错恒成立的资金/库存不变式，避免套件抖动；缺陷事实以该失败输出为准）。
