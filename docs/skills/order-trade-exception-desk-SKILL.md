# 交易异常处置规范

## 1. 用途

把交易链路上所有"不该正常发生、但必然会发生"的冲突，收拢成**一张异常表 + 一套处置动作 + 一条闭环判据**，确保任何异常都有记录、有责任人、有结果，且**不能通过修改订单状态让其消失**。

本 Skill 只管"异常识别与处置"，不重定义状态机与回调幂等（遵循 `order-state-machine`、`payment-callback-idempotency`）。

## 2. 触发场景

- 回调验签失败、金额对不上、订单号查不到，需要决定"记在哪、返回什么"。
- 订单已关闭后才到账，需要判断订单能不能恢复、库存能不能重新占用。
- 渠道退款失败，客服要重试而不是重新发起一笔新退款。
- 验收时发现"异常记录不见了"，需要判定这是缺陷还是合规处置。
- 要设计异常表的字段与状态，避免做成"日志"而失去可处置性。

## 3. 输入

| 输入 | 是否必需 | 说明 |
|---|---|---|
| 异常类型清单 | 必需 | 至少覆盖：关单后到账、无主支付、金额不符、重复扣款、验签失败 |
| 异常表结构 | 必需 | 类型、状态、关联订单、渠道交易号、双方金额、处置人、处置动作、结果、时间 |
| 处置动作清单 | 必需 | 发起原路退款、联系渠道核实、标记忽略（须填原因） |
| 状态机口径 | 必需 | 订单状态集合，用于判断"异常是否改变订单状态" |
| 处置人角色 | 必需 | 谁有权处置（本题为客服），谁只能只读（本题为运营） |

## 4. 执行步骤

### 步骤 1　识别：五类异常各判一次

对每条异常依次回答四个问题，答案决定记录与返回：

1. 钱有没有到？2. 订单还在不在合法状态？3. 金额与订单是否一致？4. 身份是否可信？

| 异常类型 | 判定条件 | 订单状态 | 账务动作 | 返回给渠道 |
|---|---|---|---|---|
| 关单后到账 | 成功通知送达时订单已关闭 | 保持已关闭 | **不入账**，落异常待客服原路退款 | 成功（渠道侧已扣款，不能让它重试） |
| 无主支付 | 通知中的订单号不存在 | 无 | 落异常，可按渠道交易号反查 | 失败码 |
| 金额不符 | 通知金额 ≠ 订单应收（含差 1 分） | 不变 | **绝不入账、绝不发货**，记录双方金额 | 失败码 |
| 重复扣款 | 同渠道交易号命中已入账订单的再次记款企图 | 不变 | 拒绝记款，落异常留痕 | 成功（但不重复入账） |
| 验签失败 | 鉴权不通过 | 不变 | 回调记录置 FAILED | **失败码**（让渠道重试） |

### 步骤 2　建档：异常表必须是"工单"而不是"日志"

每条记录必须同时具备：类型、状态（待处理 / 已闭环）、关联订单（无主支付可为空）、渠道交易号、渠道金额与系统金额、发生时间、处置人、处置动作、处置结果、闭环时间。

缺任何一项，该记录即不可处置，视为设计缺陷。

### 步骤 3　处置：动作有前提，结果要落表

| 处置动作 | 前提 | 结果 | 硬约束 |
|---|---|---|---|
| 发起原路退款 | 仅"关单后到账" | 渠道退款成功、异常闭环 | 订单**保持已关闭**；库存**不回补** |
| 联系渠道核实 | 无主支付、金额不符 | 记录核实结论 | 不得直接关闭记录而无结论 |
| 标记忽略 | 任一类型 | 记录原因 + 处置人 | 原因必填，无原因不得提交 |

一次处置只影响一条记录，不允许批量"清空异常"。

### 步骤 4　守住三条闭环红线

1. 异常记录只能经处置动作转"已闭环"，**不存在删除 / 隐藏入口**。
2. 运营侧对异常只读可见，**无改状态能力**；任何修改订单状态导致异常"看不见"的实现都判为缺陷。
3. 处置结果必须与流水一致：说退款成功，就必须有一条成功退款流水与之对应。

### 步骤 5　边界与越权一并归口

- 越权访问（买家访问他人订单、非本角色调用接口）：返回明确错误并**可查询**，不静默返回空。
- 非法迁移（表外迁移）：拒绝 + 记录日志，不得静默放行。
- 退款失败重试：**复用同一退款单**重试，不得生成第二笔退款申请。

### 步骤 6　自检清单

逐条自查并留证：

1. 五类异常是否都能主动制造并落到异常表？
2. 每条记录是否都能找到处置入口？
3. 是否存在任何"改订单状态即让异常消失"的路径？
4. 关单后到账处置完成后，库存数量是否真的没变？
5. 退款失败后重试，是否只有一条成功退款流水？

## 5. 输出格式

```
### A. 异常类型表
| 类型 | 判定条件 | 订单状态是否变化 | 账务动作 | 返回码 |

### B. 异常记录字段表
| 字段 | 必填 | 说明 |

### C. 处置动作矩阵
| 动作 | 适用类型 | 前提 | 结果 | 硬约束 |

### D. 闭环验证清单
1. ... 5.
```
评审场景输出「违规清单」：`位置 / 违反条目 / 后果（异常可被抹除、重复退款、库存超卖、验签失败仍返回成功）/ 修复建议`。

## 6. 失败处理

| 情形 | 处理 |
|---|---|
| 异常表缺状态字段（只有日志） | 判定为不可处置，先补状态字段与处置入口，再谈其他 |
| 出现"删除异常记录"或"一键清空"功能 | 直接判违规，要求移除 |
| 无主支付无法反查 | 判缺陷：必须以渠道交易号可反查 |
| 迟到退款后被要求"顺便恢复库存" | 明确拒绝，注明会直接导致超卖 |
| 渠道要求对迟到通知返回失败码 | 说明会导致渠道重复重试与二次扣款，坚持返回成功 |
| 不知该归到哪类异常 | 落表并标记类型"未分类 + 原因"，禁止丢弃 |

## 7. 完成标准

1. 五类异常全部可被主动注入复现，且逐条有记录、有处置、有结果。
2. 异常记录无法被删除或隐藏，只能经处置动作闭环。
3. 关单后到账处置后：订单仍已关闭、库存数量不变、无第二条退款流水。
4. 退款失败重试路径可复现：失败保持原状态、重试成功仅一条流水。
5. 越权与非法迁移均有明确错误返回且可查。
6. 运营侧对异常只读，实测无法改状态。
