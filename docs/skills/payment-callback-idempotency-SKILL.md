# Payment Callback Idempotency（支付回调幂等与异常通知处理）

## Overview

本技能提供对接第三方支付渠道时异步通知处理的完整标准：幂等三道防线、固定顺序的处理流程、响应约定、异步边界、支付异常表与禁止事项。核心原则：**每笔通知先落库再处理，任何失败可重放；重复、并发、迟到通知均不得产生重复的资损动作。**

## 适用场景

- 对接第三方支付渠道的异步成功/失败通知
- 渠道网络重试导致重复通知、并发通知、乱序通知
- 订单已关闭/已退款后才到达的成功通知
- 金额不符、找不到订单、验签失败、重复扣款

## 幂等三道防线（必须全部具备）

1. **入口幂等**：以渠道流水号 `channel_trade_no` 建唯一索引，插入失败即判定重复，直接返回成功响应，不进入业务逻辑。
2. **处理幂等**：回调记录表状态 `RECEIVED → PROCESSING → DONE / FAILED`，用条件更新抢占处理权；已是 DONE 的直接返回成功。
3. **结果幂等**：订单状态迁移本身使用条件更新（见 order-state-machine），重复执行时受影响行数为 0，视为已处理。

## 处理流程（固定顺序，不得调整）

1. 第一步就持久化原始报文到回调记录表（含请求体、头、渠道流水号、时间），后续任何失败都可重放。
2. 验签；失败则记录 FAILED 并返回失败码（渠道会重试，不要吞掉）。
3. 按订单号查订单；订单不存在 → 落支付异常表，类型"无主支付"。
4. 比对金额与币种；不一致 → 落异常表，类型"金额不符"，绝不入账、绝不发货。
5. 判断订单状态：`CREATED → 置 PAID`；`CLOSED / REFUNDED / COMPLETED` → 落异常表，类型"关单后到账"，订单状态保持不变。
6. 全部成功 → 回调记录置 DONE → 返回成功响应。

## 响应约定

- 已处理过 / 判定为重复：返回成功（阻止渠道无限重试）
- 验签失败、系统异常、处理未完成：返回失败码（让渠道重试）
- 严禁"先返回成功、后台异步处理但不落表"，否则通知丢失后无法追溯

## 异步边界

回调内只做：落库、验签、状态迁移、写流水。

发货通知、短信、库存实物操作等长耗时动作一律投递异步任务，不得在回调链路内同步执行。

## 支付异常表（必须存在，不允许只打日志）

字段：异常类型、订单号、渠道流水号、渠道金额、系统金额、原始报文引用、状态、处理人、处理结果、处理时间。

异常类型至少覆盖：关单后到账、无主支付、金额不符、重复扣款、验签失败。

客服处置动作：原路退款 / 手工补单 / 联系渠道核实 / 标记忽略（须留原因）。

每笔异常必须有可查记录并能闭环，不允许"渠道已收款但系统查不到有效订单"长期悬空。

## 禁止事项

- 禁止用订单状态充当回调幂等键
- 禁止仅靠渠道通知次数或时间去重
- 禁止在重复通知时再次扣库存、再次写支付流水
- 禁止验签失败却返回成功

## 验收用例

实现或评审回调逻辑后，逐条验证以下用例：

1. 同一笔通知连续推送 5 次 → 订单只进入 PAID 一次，支付流水只有一条。
2. 同一笔通知 3 路并发到达 → 只有一路处理成功，其余返回成功但不重复入账。
3. 订单已关闭后通知到达 → 订单仍为 CLOSED，异常表新增"关单后到账"记录。
4. 通知金额与订单金额差 0.01 → 不入账，异常表新增"金额不符"。
5. 订单号不存在 → 异常表新增"无主支付"，可用渠道流水号反查。

## 硬性规则

- 处理流程的六步顺序固定，不得调整；原始报文必须最先落库。
- 幂等三道防线缺一不可，实现时逐条检查。
- 支付异常表必须存在，所有异常类型必须可查、可闭环，不允许只打日志。
- 与订单状态迁移对接时遵循 order-state-machine 技能的迁移表。
