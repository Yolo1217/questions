# 订单交易主链路业务口径

## 1. 用途

为「小型电商 · 订单交易 / 发货 / 售前退款」类项目提供**可执行的业务裁决口径**：明确每个动作的准入条件、必须产生的副作用、以及并发下唯一合法的结果，避免实现时出现超卖、重复入账、重复退款、已退款仍发货。

本 Skill 只定义**业务裁决**，不定义状态机全集与回调幂等的完整规则。这两部分遵循项目已安装的：

- `order-state-machine`：状态最小集、迁移表、非法迁移拒绝与记录。
- `payment-callback-idempotency`：幂等三道防线、回调六步流程、支付异常表、响应约定。

本 Skill 与上述两个 Skill 是引用关系，不复制、不覆盖其内容。

### 1.1 口径优先级（与通用技能的已知冲突）

上述两个 Skill 是**通用**标准，本题对其做了裁剪。两者冲突时**以本 Skill 为准**，已识别三处：

| 冲突点 | 通用技能（order-state-machine） | 本题口径（以本 Skill 为准） |
|---|---|---|
| 签收态 COMPLETED | 包含 `SHIPPED → COMPLETED` | **不存在**，本题不做签收/售后 |
| 退款受理范围 | 允许 `PAID / SHIPPED → REFUNDING` | **仅 `PAID`**；`SHIPPED` 一律拒绝售前退款 |
| 异常的表达 | 支付冲突迁移到订单状态 `EXCEPTION` | 用**独立支付异常表**承载，订单状态保持 6 码不变 |

## 2. 触发场景

- 要写下单接口 / 库存扣减逻辑，但不确定预占与实扣的边界。
- 要写支付回调入账，需要确认"金额、订单、状态"三者的判定顺序。
- 要实现售前整单退款，需要区分"售前可回补库存"与"迟到支付退款不回补"。
- 要实现发货登记，需要确认并发下退款与发货只能活一个。
- 要做 code review 或验收，需要一份可逐条对照的红线口径。

## 4. 执行步骤

### 步骤 1　先钉死四条不变量

在写任何代码前，把下面四条写成断言或测试用例，后续所有实现都必须满足：

1. 任一时刻 `可售数量 = 现存 − 预占 − 实扣`，且 `可售数量 ≥ 0`。
2. 同一渠道交易号**只能**归属一个订单、只入账一次。
3. 同一订单**最多**一条成功支付流水、最多一条成功退款流水。
4. 非 `PAID` 状态**不存在**合法发货路径；`SHIPPED` 状态**不存在**合法售前退款路径。

### 步骤 2　下单（预占）

1. 校验商品存在且在售；校验数量在允许区间；校验 `available ≥ qty`。
2. 用**条件扣减**完成预占：`UPDATE stock SET available = available - :qty WHERE sku = :sku AND available >= :qty`，受影响行数 = 0 即"库存不足"，**不产生订单**。
3. 订单必须保存**下单时快照**（商品名、单价），后续调价不影响已存在订单金额。
4. 写库存流水（动作 = 预占、数量取负），写订单（状态 = 待支付）与到期时间，三步在同一事务内。

### 步骤 3　支付入账（预占转实扣）

1. 先落原始报文，再验签；验签失败**返回失败码**，绝不返回成功。
2. 匹配订单、比对金额与币种（差 1 分也算不符）→ 不符即落异常表，**不入账、不发货**。
3. 订单状态以条件更新迁移（`WHERE status = 待支付`）；受影响行数 = 0 视为已处理，返回成功但不产生新的账务动作。
4. 入账成功写支付流水（渠道交易号唯一），并把预占记为实扣（库存总量不变，只改占用归属）。

### 步骤 4　发货

1. 只允许 `PAID` 进入：`UPDATE orders SET status = 已发货, carrier = ?, tracking_no = ? WHERE id = ? AND status = 'PAID'`。
2. 受影响行数 = 0 时，回查当前状态并返回**具名错误**：退款处理中 / 已关闭 / 已退款，逐一如实告知，不产生运单。
3. 承运方与运单号必填；每单仅一次，重复登记按受影响行数 = 0 拒绝。

### 步骤 5　售前退款

1. 准入：仅 `PAID` 且整单；`REFUNDING` 期间冻结发货（发货条件更新自然失败）。
2. 受理即迁移到 `REFUNDING`，写退款申请单；重复受理被条件更新拒绝，**不产生第二笔**。
3. 客服拒绝：回 `PAID`，必须记录拒绝原因，订单重新可发货。
4. 渠道成功：迁移 `REFUNDED`，写退款流水，**回补可售数量**，写库存流水（动作 = 退款回补、数量取正）。
5. 渠道失败：**保持 `REFUNDING`**，写失败记录并保持"待处理"，允许重试；重试成功后才迁移与回补。

### 步骤 6　迟到支付与库存释放边界

1. 超时或买家取消 → `CLOSED` 并释放预占；释放同样用条件更新，重复执行不重复释放。
2. 订单 `CLOSED` 后到达的成功通知：订单**保持 `CLOSED`**，落异常表「关单后到账」，**不恢复订单、不重新占用库存**。
3. 客服对该异常发起原路退款成功后：异常记录闭环，库存**数量不变**（关单时已释放，再回补即超卖）。

### 步骤 7　自检

用步骤 1 的四条不变量逐条跑断言；对每个写入口问三个问题：准入条件是什么、失败时返回什么、并发下凭什么只有一个成功。

## 6. 失败处理

| 情形 | 处理 |
|---|---|
| 无法确定库存是"预占"还是"实扣" | 停止实现，先确认模型；未区分占用归属时一律按预占处理，付款后转实扣 |
| 状态机未给出对应迁移 | 拒绝实现该路径，按非法迁移处理并记录；不得自造迁移 |
| 存在部分退款/售后诉求 | 超出本题范围，明确拒绝并指出与"仅整单售前退款"的冲突 |
| 并发下无法用条件更新表达 | 退回需求方确认是否允许引入分布式锁；默认**禁止**引入 |
| 金额出现浮点 | 立即停止，改为整数分；浮点即视为缺陷 |
| 校验发现已上线数据违反不变量 | 只出修复方案与影响范围，**不直接改数据**，等确认 |
