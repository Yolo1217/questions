# 交易项目自验收检查规范

## 1. 用途

用**独立会话**对交付物做一次可复核的取证式验收：只认代码、日志、流水、测试报告与运行结果，**不采信任何"已完成"的口头声明**。产出逐项 PASS/FAIL 的验收报告与缺陷清单。

与 `student-project-audit`（教师评分工具）的区别：本 Skill 是**学生自验收**用途，不产出评分与排名，只回答"哪一项没有证据"。

## 2. 触发场景

- 开发 Agent 声称完成，需要独立判定是否真的满足验收条件。
- 上线前自检：六场景是否都能演示、十八边界是否都能复现。
- 整改后复验：确认上轮 FAIL 项是否真修复，且未引入新问题。
- 要写验收报告但缺少统一的判定口径与证据要求。

## 3. 输入

| 输入 | 是否必需 | 说明 |
|---|---|---|
| 原始题面 | 必需 | 判定基准，不读题面不开始验收 |
| 最终版本标识 | 必需 | 提交号或版本号，验收对象必须唯一确定 |
| 代码与运行环境 | 必需 | 可启动、可访问，或可复现的测试入口 |
| 需求与原型文档 | 必需 | 用于核对设计口径与实现是否一致 |
| 上轮验收报告 | 复验时必需 | 用于只复核既有 FAIL 项，不重刷全部 |
| 证据材料 | 必需 | 测试报告、覆盖率、流水截图、日志、部署地址与冒烟结果 |

## 4. 执行步骤

### 步骤 1　先判红线（一票否决）

任一条成立，整份验收直接不通过，无需继续逐项打分：

1. 超卖，或库存总量与库存流水不吻合。
2. 重复记款或重复退款。
3. 已退款仍可发货，或退款处理中发货未被拒。
4. 关单后到账恢复订单，或重新占用已释放库存。
5. 迟到支付退款回补了库存。
6. 验签失败仍返回成功。
7. 异常记录可通过直接改状态而消失。

### 步骤 2　六场景逐项取证（S1–S6）

每项都必须给出**可复现路径 + 观测到的证据**，缺证据即 FAIL，不以"看起来对"通过。

| 编号 | 检查项 | 通过判据（须有证据） |
|---|---|---|
| S1 | 正常成交 | 上架 → 下单付款 → 状态为待发货、库存实扣 → 发货登记 → 买家可见承运方与运单号 → 运营已收款合计与支付流水一致 |
| S2 | 缺货与弃单 | 20 并发争 5 件：恰 5 单成功、其余明确拒绝；未付订单关闭后库存释放且可被再次购买；可售数量从未为负 |
| S3 | 售前退款 | 申请后发货被拒 → 客服批准 → 首次失败仍保持退款中且留待处理 → 重试成功 → 已退款、可售恢复、买家可见结果 |
| S4 | 迟到支付 | 订单关闭后收到成功通知：订单仍关闭、异常表新增关单后到账 → 客服原路退款闭环 → 库存数量无变化、无第二条退款流水 |
| S5 | 操作竞争 | 退款与发货并发只产生一种合法结果；重复通知不重复入账；越权访问被拒且错误可查 |
| S6 | 运营核查 | 按订单可查收款、退款、发货、异常四类记录；异常只能经处置闭环；可售数量、已收款、已退款汇总与流水吻合 |

### 步骤 3　十八项边界逐条复现（E01–E18）

逐条给出：操作路径、预期、实际、结论。任何一条**未实测**即记 FAIL（未验证 ≠ 通过）。

E01 超量下单拒单且不产单｜E02 下架商品拒单｜E03 20 并发不超卖｜E04 超时自动关闭并释放｜E05 重复关闭不重复释放｜E06 同通知连推 5 次仅一条流水｜E07 三路并发仅一路生效｜E08 关单后到账入异常且订单不变｜E09 金额差 1 分不入账｜E10 无主支付可按渠道交易号反查｜E11 验签失败返回失败码｜E12 退款与发货并发只出一种结果｜E13 重复退款仅一条流水｜E14 首次退款失败可重试成功｜E15 越权明确拒绝｜E16 异常不可被改状态抹除｜E17 调价后已有订单金额不变｜E18 已发货订单拒绝售前退款。

### 步骤 4　非业务项取证

| 检查项 | 判据 |
|---|---|
| 单元测试覆盖率 | 整体与各核心包均达门槛，报告可查；集成测试不计入覆盖率 |
| 测试真实性 | 抽查用例是否断言业务结果，而非只断言返回 200 |
| 文档一致性 | README 索引的文件**真实存在**；文档描述与代码行为一致 |
| 流程留痕 | 版本控制记录、分支、工作项核验、门禁与部署记录齐备可查 |
| Skill 使用留痕 | 至少两个自编 Skill（业务 + 验收）有真实调用记录与问题修正回环 |
| 部署冒烟 | 有可访问地址与冒烟结果，非本地截图替代 |

### 步骤 5　出报告

按证据分档，不写模糊措辞：
- **PASS**：有可复现证据。
- **FAIL**：实测不符，或明确缺失。
- **UNVERIFIED**：无法实测（环境不可用、证据缺失）——按不通过计，并写明复测条件。

### 步骤 6　复验纪律

整改后只复核上轮 FAIL / UNVERIFIED 项 + 回归红线；**不对已 PASS 项做重写或扩大范围整改**，避免问题计数反复。

## 6. 失败处理

| 情形 | 处理 |
|---|---|
| 无法启动或访问环境 | 记 UNVERIFIED 并按不通过计，写明复测所需条件，不臆测通过 |
| 缺少覆盖率报告 | 直接 FAIL，不接受口头说明 |
| 证据只有截图无日志/流水 | 记为弱证据，关键项（红线、S2/S4）不接受 |
| 发现红线问题 | 立即停止逐项打分，先出红线报告 |
| 与开发 Agent 同会话 | 立即中止：验收必须换独立会话，避免继承开发侧结论 |
| 题面与需求文档冲突 | 以**原始题面**为准，并单列文档偏差项 |
| 请求放宽某项判据 | 拒绝，判据以题面为准；如需裁剪须留书面说明 |

## 7. 完成标准

1. 红线七条逐条给出结论与证据。
2. S1–S6 全部有可复现路径与证据，无一项为"未实测"。
3. E01–E18 全部实测，逐条给结论。
4. 非业务项六类均有证据，覆盖率与部署冒烟无缺失。
5. 每条 FAIL / UNVERIFIED 均指明位置、后果与复测条件。
6. 报告结论明确写出「通过 / 不通过」，不含模糊表述；且验收在独立会话完成，未采信开发侧声明。
