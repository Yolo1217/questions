# 题目 01 业务实现说明：小型电商订单交易、发货与售前退款

> 在 `bw-cli`（Gin + gRPC + Gorm，DDD 分层）脚手架内落地的交易域实现。
> 数据库：本地 MySQL `root/root`，库 `questions`；单元测试库 `questions_test`（首次运行自动创建）。

## 二、核心设计

### 2.1 状态机（唯一迁移入口）

| 事件 | from | to | 必要副作用 | 实现 |
|---|---|---|---|---|
| 下单 | — | CREATED | 预占库存 + 库存流水 | `PlaceOrderTx`（事务内条件扣减） |
| 支付成功 | CREATED | PAID | 预占转实扣 + 支付流水 | `TransitionOrder` + mutate 写台账 |
| 支付成功 | CLOSED/REFUNDED | 保持原状态 | 落「关单后到账」异常，不恢复订单、不占用库存 | `PayNotify` default 分支 |
| 支付成功 | PAID/SHIPPED/REFUNDING | 保持原状态 | 落「重复扣款」异常，返回成功不重复记款 | `PayNotify` 分支 |
| 买家取消 / 超时 | CREATED | CLOSED | 释放预占（只释放一次） | `CancelOrder` / `SweepExpired` |
| 申请退款 | PAID | REFUNDING | 冻结发货 | `ApplyRefund` |
| 退款成功 | REFUNDING | REFUNDED | 售前退款回补库存；迟到退款不回补 | `AuditRefund`（按 `origin` 判定） |
| 渠道退款失败 | REFUNDING | REFUNDING | 写失败流水 + `refund_fail` 标记，可重试 | `MarkRefundFailed` |
| 客服拒绝退款 | REFUNDING | PAID | 记录原因，恢复可发货 | `AuditRefund(approve=false)` |
| 仓库发货 | PAID | SHIPPED | 写承运方 + 运单号，每单一次 | `ShipOrder` |
| 重复退款通知 | REFUNDED | REFUNDED | 幂等成功，不重复打款、不回补库存 | `AuditRefund` 幂等分支 |

所有迁移都通过：

```sql
UPDATE shop_trade_orders SET status = ? WHERE id = ? AND status = ?
```

受影响行数为 0 即视为非法/重复迁移并拒绝，因此并发下同一订单只会产生一种合法结果。

### 2.2 库存一致性

- 预占：`UPDATE shop_products SET available = available - ? WHERE id = ? AND available >= ?`，rows=0 → `insufficient_stock`，不产生订单（20 并发抢 5 件只成功 5 单）。
- 实扣：支付成功仅写「预占转实扣」台账，不再扣减 `available`。
- 释放：取消/超时 `stockDelta=+qty`，与状态迁移同事务，重复关闭不再释放。
- 回补：仅 `origin=sale` 的售前退款回补；`origin=late`（迟到支付退款）`stockDelta=0`。
- 对账：运营汇总返回 `available_total`（可售）+ `reserved_total`（待支付预占件数），二者与 `total` 可互校。

### 2.3 支付回调：HMAC 验签 + 固定六步 + 幂等三道防线

签名算法（渠道与商城共享密钥 `TRADE_CHANNEL_SECRET`，默认 `shop-mock-channel-secret`）：

```text
signature = hex( HMAC-SHA256( secret, "channel_trade_no|order_id|amount_cents" ) )
```

服务端**自行重算比对**（`subtle.ConstantTimeCompare`），不信任调用方任何"已验签"声明；签名为空或不匹配一律判失败。

| 步骤 | 动作 | 失败处理 |
|---|---|---|
| 1 | 持久化回调记录（主键 `channel_trade_no`） | 主键冲突 → 判定重复：**仅累加命中次数**，返回成功（入口幂等） |
| 2 | 重算 HMAC 验签 | 记录 `FAILED`，落「验签失败」异常，返回失败码 |
| 3 | 查订单 | 不存在 → 落「无主支付」，返回失败码 |
| 4 | 比对金额（含币种单位：分） | 不一致 → 落「金额不符」，绝不入账/发货 |
| 5 | 状态分流 | CREATED → PAID；已收款 → 「重复扣款」；CLOSED/REFUNDED → 「关单后到账」 |
| 6 | 全部成功 → 回调记录 `DONE` | 返回成功 |

- 处理幂等：回调记录 `RECEIVED → DONE/FAILED`；重复通知只 `hits+1`，**不会把 DONE 降级回 RECEIVED**。
- 结果幂等：订单状态条件更新，rows=0 视为已处理（并发 3 路只迁移一次）。
- 同一渠道交易号主键唯一，天然保证「不得归属两个订单」。
- 反查：`GET /api/v1/cs/callbacks/{tradeNo}` 返回 `RECEIVED/DONE/FAILED`、命中次数、关联异常类型与状态；无主支付没有订单也能查。

### 2.4 支付异常表与客服闭环

五类异常：关单后到账 / 无主支付 / 金额不符 / 重复扣款 / 验签失败。
处置动作：`refund`（仅限有订单的异常）/ `verify`（联系渠道核实）/ `ignore`（标记忽略）。
**三个动作都必须有原因**（`refund` 未填时记为「核实后原路退款」），并写入处理人与结论；有订单的异常同时向订单台账追加 `exception` 条目，运营按订单即可看到「谁、何时、以什么原因处理了哪笔异常」。
`CloseException` 使用 `WHERE status='待处理'` 条件更新，重复处置被拒绝，异常记录无法通过改订单状态让其消失。

### 2.5 角色鉴权与越权控制

- 登录时把 `user_id / role / name` 写入 JWT；网关 `RequireRole` 按角色拦截，未命中直接 401/403 且不转发到 gRPC。
- 买家下单、取消、申请退款：`buyer_id` 一律取自 JWT，请求体不能指定他人。
- 买家查看详情：网关比对 `buyer_id`，不符返回 403。
- 客服/仓库/运营列表由服务端按状态过滤（仓库只拿到 PAID、客服只拿到 REFUNDING）。

## 七、边界与未实现项

- 支付渠道为模拟实现：验签使用**共享密钥 HMAC-SHA256**，与真实渠道的证书/非对称签名不同；无渠道清算文件与对账单下载。
- 仅单商品、数量 1~2 件、人民币分，不含运费/优惠/购物车/多商户。
- 不做签收、退货、售后物流与部分退款；订单终态为 CLOSED / REFUNDED / SHIPPED。
